# Transit Games: project notes for Claude

Companion site for city-scale transit games (Rail Rush, Area Claiming, Ticket to Ride). Static site on Vercel; data and sign-in on Firebase (Firestore + Auth). No server code.

## Layout
- `src/shell.html`: home, start/ongoing/past lists, create-game dialog, account dialog, light/dark toggle. Each game runs in an iframe (`srcdoc`) inside it.
- `src/rail-rush.html`, `src/area-claiming.html`, `src/ticket-to-ride.html`: one self-contained file per game (HTML + CSS + JS).
- `src/map-editor.html`: the Map Editor (opened from the home screen in its own frame, like a game). Maps live in `maps/{id}` (owner, name, `json` string holding the Rail Rush map format, `share` = `private`|`link`; challenges will go in `maps/{id}/challenges`). Share links are `/#map=<id>`. Six built-in maps are built by `src/cities.mjs` (called from `build.mjs`) from the NETS in `src/rail-rush.html`: Toronto/Boston/Montréal, each as `-Augmented` (everything) and `-Base` (main rail lines only), with Red, Green, Silver and REM merged into branching lines; offered as "Edit a city" (always opens the user's own copy). Montréal-Augmented also has stop-by-stop buses 141, 12, 35, 48/49 and 206 from `src/mtl-buses.mjs`, and no 815: the 209 runs Pierrefonds–Roxboro > Des Sources > YUL (the Des Sources–YUL stops are STM's, thinned from 24 to 13 keeping Terminus Dorval) (stop positions approximate; thinned evenly, interchanges kept) and a straightened, thinned 121/215. Rail Rush has these six embedded too (`MAPS`, injected by `build.mjs`). New Rail Rush games are created with no map: the host picks one in the game (built-in, one of their own `maps`, or someone else's shared link) until the game starts (changing it after challenges were added deletes them, after a strong warning); the game doc gets `mapKey` (built-in key or `custom`), `mapName`, `mapRev`, `mapFrom`, and a custom map is copied to `games/{gid}/mapdata/cur` (`json`). Old games keep `city` and the original NETS. Test: `test/t_mapchoice.py`. Branches may carry an optional `name`; a branch can have several pieces (several `branches` entries sharing a `group` string, e.g. Boston Green D and E, which leave the trunk at two places): one branch for transfer purposes, one name. Test: `python3 test/t_branchgroups.py`. Test: `node test/t_cities.mjs`. The map is stored as a JSON string on purpose: Firestore rejects nested arrays and the string keeps the size measurable (limit 900 KB).
- Rail Rush host options (game doc): `pinkOn` (Get here! switch; new games get `false` from `shell.html`, games without the field count as on), `endMode` (`''`|`duration`|`time`) with `endMin` or `endAt`; the deadline is `startedAt + endMin` or `endAt` (`deadline()`), `RO()` is true from then on and `fold()` is cut at the deadline. Whoever has the game open ends it (`finishGame(deadline, true)`, host first, others after 4 s) and the header shows a countdown. Get here!: the claiming team writes the claim and the next station (`pc_` event); other clients only fall back (`pf_`) after 10 s; the next station avoids the previous one's line(s) when it can (`planPink` tiers). On the Gameboard the default amount is the leader's lead + 1 when another team leads (`S.amt == null` means default). Tests: `test/t_gamefeatures.py`, `t_pinkclaim.py`, `t_pinkmove.py`.
- Challenge locations (Rail Rush): a challenge doc has `loc` (station ids), `lines` (line ids; a line means a random station on it, picked when the challenge goes live; `candOf()` is the pool) and `locText` (unmatched text). In `parseLoc`, a bare name is a station first, then a line; `Name (Route)` (or `(Line)`) forces the line; a name shared by several branch pieces means all of them. The Get here! switch (`pinkOn`) is fixed once the game starts. After the start, anyone with the password can still join (`mayEnter` in `shell.html`), but teams stay locked: they get a teamless `players/{uid}` doc (`autoReg`, name editable) and the host adds them from the Host tab (`renderSpec`). Tests: `test/t_lines.py`, `test/t_lock.py`.
- Admin (phase 1, read-only): an account is an admin when `admins/{uid}` exists (added by hand in the Firebase console; clients can read only their own entry and never write it; guests never count: see `isAdmin()` in `firestore.rules`). The shell reads it at sign-in (`data.admin`) and shows an Admin button that opens `src/admin.html` in its own frame (games list with filters, game details, all maps, stats). Admins open any game through `TG.openGame` without the password and without a members/players entry; in Rail Rush `VIEW()` turns off spawning, expiry and auto-end writes for such a viewer. Joining as an admin is refused with a notice. The rules for `games` are still open to any signed-in user: tightening them (host-only fields, per-role events) and the admin actions (end/delete game, reset password, remove/move players, delete map, an admin-only audit log, admin edits credited to 'Admin' in the game log) are the next phases; so is letting a host remove players. The free Firebase plan has no Cloud Functions, so game passwords stay a client-side gate. Tests: `test/t_admin.py`; `test/rules.test.mjs` needs the Firebase emulator (run locally).
- `src/platform.js`: the ONLY file that talks to Firebase. Provides `claude.use('db')` (a Firestore instance) and `claude.use('user')` (`id()`), plus `window.TGAuth` for accounts. Games use `db.doc/collection/onSnapshot/get/set/update/delete/add/where`.
- `src/firebase-config.js`: Firebase web config (not secret).
- `firestore.rules`: security rules; paste changes into Firebase console > Firestore > Rules. Games and hides stay open to any signed-in user; `maps` are owner-only unless `share == 'link'` (then readable by id, never listable), and only non-guest accounts can create or change them. Do not add a catch-all `/{document=**}` rule: it would override the map rules.
- `build.mjs`: `npm run build` embeds the games, config and platform into `public/index.html`. `public/` is generated: never edit it.
- `test/`: Python + Playwright tests with a mock shared database (`harness.py`). Run `python3 test/t_full.py` (also `t_3team.py`, `t_area.py`, `t_boston.py`, `t_theme.py`, `t_maps.py`) after `npm run build`. Needs `pip install playwright && playwright install chromium`.
- `tools/`: Boston map data (`boston.json`) already embedded in Rail Rush; kept for reference.

## Working rules
- Edit files in `src/`, run `npm run build`, run the relevant tests, then deploy.
- Data lives under `games/{gid}/...` (events, players, teams, challenges, members) and `hides/`. Rail Rush state is derived from an append-only `events` log by the pure function `fold()`; change rules there, not by mutating stored state.
- Keep games free of Firebase imports; add any new backend capability in `platform.js`.
- Once a Rail Rush game has started, teams are locked (`teamsLocked()`): no joining or switching, except for players whose team the host removed. The game doc gets `startedAt`. Anyone with the password can still join a started game, but only as a spectator (see below). Tests: `test/t_lock.py`.
- Do not use `alert/confirm/prompt`; use in-page dialogs.
- Deploy: commit and push to GitHub; Vercel builds automatically (`vercel.json`).
- Inactivity: `platform.js` stamps `games/{gid}.lastActive` on any write inside a game (throttled to 5 min). `shell.html` ends games idle for 7 days (run by whoever has the site open; `endIdle`) and lets members reset the clock after 1 day (`resetIdle`, banner + Ongoing list). Games without a stamp get a fresh 7 days. Tests: `test/t_idle.py`, `node test/t_touch.js`.
